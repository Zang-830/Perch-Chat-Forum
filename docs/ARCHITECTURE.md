# 架构与扩展约定

## 当前结构

项目采用前后端分离的模块化单体架构。后端按业务域组织，而不是把所有 Controller、Service、Mapper 分别堆到同一目录；前端按页面、公共组件、状态和 API 分层。

```text
backend/com/campus/community/
├─ auth/       注册、登录和令牌
├─ user/       用户与公开资料
├─ category/   社区频道
├─ post/       帖子与点赞
├─ comment/    评论
├─ file/       图片校验、存储与归属
├─ report/     内容举报
├─ admin/      运营统计与审核操作
├─ security/   统一鉴权
├─ common/     返回结构与异常处理
└─ health/     运行状态检查
```

模块之间只通过明确的 Service 能力交互。例如评论模块通过 `PostService` 检查帖子是否可用，不直接复制帖子状态规则。

## 新增二手市场

建议新增以下独立结构：

```text
market/
├─ controller/
├─ dto/
├─ entity/
├─ mapper/
└─ service/
```

核心表建议包含 `market_items`、`market_item_images`、`market_favorites` 和 `market_orders`。商品拥有独立状态机：`DRAFT → ON_SALE → RESERVED → SOLD`，也允许从在售状态进入 `OFF_SHELF`。

二手市场复用以下公共能力：

- 账号与 JWT 鉴权；
- 图片文件服务；
- 违规举报与内容审核；
- 站内通知；
- 校园身份与信用信息。

不要把价格、成色、交易地点等字段加入 `posts` 表。若希望商品出现在社区信息流，可以让商品记录保存一个可选的 `post_id`，或在聚合查询层统一生成信息流卡片。

## API 约定

- 接口统一以 `/api` 开头；
- 成功业务码为 `0`；
- 分页参数统一使用 `page` 和 `size`；
- 列表返回 `items / total / page / size`；
- 数据库变更只能新增 Flyway 版本脚本，已发布脚本不回改；
- 前端只通过 `src/api` 访问后端，不在页面内散落请求地址。

## 文件与审核边界

- 上传接口只接受 JPG、PNG、GIF，并同时检查 MIME、文件签名、真实图片尺寸和大小；
- 数据库只保存文件元数据和访问路径，原始文件存放在 `UPLOAD_DIRECTORY`；
- 帖子只能关联当前用户自己上传且状态正常的文件；
- 管理员可以隐藏帖子、封禁用户、处理举报，但不能封禁管理员或修改自己的状态；
- 鉴权过滤器每次请求都会读取最新用户状态，因此封禁后已有令牌也会立即失效；
- 生产环境应使用对象存储、病毒扫描、缩略图任务和定期孤立文件清理替代本地存储实现。

## 后续优先级

1. 文件上传和图片缩略图；
2. 管理员审核、举报处理和用户禁言；
3. 站内通知与未读数；
4. 个人主页、收藏和历史记录；
5. 二手市场首版；
6. 失物招领与校园活动。
